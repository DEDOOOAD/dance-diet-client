기록 조회용 DB/서버 정리 메모
작성일: 2026-05-18

1. 현재 DB 구조를 보고 바로 보이는 점

- 운동 기록 원본 테이블은 exercise_sessions 로 보임
  - session_id
  - user_id
  - class_id
  - started_at
  - ended_at
  - duration_seconds
  - burned_kcal
  - genre

- 식단 기록 원본 테이블은 DailyFoodLog 로 보임
  - UUID
  - Day
  - FoodName
  - Calories
  - File_Path
  - Bucket_Name

- 프로필/체중 관련 테이블이 2벌처럼 보임
  - profiles
  - Profile
  - 지금 서버 코드도 SignUp / Profile / DailyFoodLog 쪽을 많이 쓰고 있음
  - auth.users + profiles 계열과 기존 SignUp / Profile 계열이 같이 존재하는 상태로 보임

- 기록 조회 관점에서 가장 중요한 건 exercise_sessions 를 월별/일별로 잘 조회할 수 있게 만드는 것임


2. 기록 조회용으로 DB를 어떻게 바꾸면 좋은가

가장 덜 위험한 방법:
- 기존 exercise_sessions 를 기록 조회의 기준 테이블로 유지
- 여기에 기록 화면에서 필요한 컬럼만 몇 개 추가
- 별도의 records 테이블을 새로 만들지 않고 먼저 조회 API를 붙임

추천 이유:
- 이미 session end 시점 저장 로직이 exercise_sessions 로 들어가고 있음
- 중복 테이블을 또 만들면 저장/조회 경로가 두 벌이 됨
- 지금은 "운동 세션 기록 = 기록 탭 데이터 원본"으로 잡는 게 가장 단순함


3. exercise_sessions 에 권장 추가 컬럼

현재 컬럼만으로도 최소 조회는 가능하지만, 기록 화면 품질을 높이려면 아래 추가를 권장

[필수에 가까움]
- movement_score numeric 또는 int4
  - 기록 상세나 정렬 기준으로 쓰기 좋음

- total_frames int4
  - 디버그/분석용. 없어도 되지만 있으면 좋음

- created_at timestamptz default now()
  - 행 생성 시각

[있으면 좋음]
- dance_name text
  - 당시 세션에 보여준 수업명/영상명을 스냅샷으로 저장
  - Dance_class.title 을 조인해서 가져와도 되지만, 나중에 원본 제목이 바뀌면 과거 기록 표시가 흔들릴 수 있음

- user_weight_kg numeric
  - 당시 유저 체중을 같이 기록하면 분석 일관성이 좋아짐

- source text
  - live-session / manual / imported 같은 구분용


4. exercise_sessions 는 이렇게 정리하는 것을 권장

권장 컬럼 예시:

- session_id uuid primary key
- user_id uuid not null
- class_id text null
- dance_name text null
- genre text null
- started_at timestamptz not null
- ended_at timestamptz not null
- duration_seconds int4 not null default 0
- burned_kcal numeric not null default 0
- movement_score numeric null
- total_frames int4 null
- user_weight_kg numeric null
- source text null default 'live-session'
- created_at timestamptz not null default now()


5. 인덱스는 꼭 추가 권장

기록 조회는 거의 항상 "유저 + 기간" 조건이라 인덱스가 중요함

필수 추천:
- create index idx_exercise_sessions_user_started_at on exercise_sessions(user_id, started_at desc);

보조 추천:
- create index idx_exercise_sessions_user_genre_started_at on exercise_sessions(user_id, genre, started_at desc);

체중 기록용 테이블을 만들면:
- create index idx_weight_history_user_measured_at on weight_history(user_id, measured_at desc);


6. class_id 와 Dance_class 연결도 점검 필요

이미지상:
- exercise_sessions.class_id = text
- Dance_class.videoId = text

이 구조면 조인은 가능함
- exercise_sessions.class_id = Dance_class.videoId

권장:
- class_id 가 실제로 videoId 를 저장하도록 규칙 고정
- 아니면 컬럼명을 content_id 또는 video_id 로 바꿔 의미를 명확히 하기


7. 체중 추이용은 별도 테이블 만드는 걸 권장

지금은 Profile / profiles 에 현재 체중만 있는 구조에 가까움
하지만 기록 탭의 "체중 추이"는 히스토리가 필요함

추천 신규 테이블:
- weight_history

권장 컬럼:
- id uuid primary key
- user_id uuid not null
- measured_at timestamptz not null
- weight_kg numeric not null
- target_weight_kg numeric null
- note text null
- created_at timestamptz not null default now()

이유:
- 현재 체중(Profile)과 과거 체중 히스토리(weight_history)는 성격이 다름
- 현재값만 Profile 에 두고, 추이는 별도 테이블로 관리하는 게 조회/확장 모두 편함


8. 식단 기록도 날짜 타입을 점검

DailyFoodLog.Day 가 timestamp 로 보이는데,
일별 기록 조회를 많이 할 거면 아래 중 하나가 더 편함

방법 A
- Day 를 그대로 timestamptz 로 두고 날짜 범위 조건 사용

방법 B 권장
- meal_date date 컬럼을 별도 추가

권장 이유:
- "2026-05-18 하루 기록" 같은 조회가 단순해짐


9. Profile / profiles 중 하나로 정리 권장

지금 구조는
- 기존 앱용 SignUp / Profile
- auth.users / profiles

두 체계가 섞여 있는 모습임

권장 방향:
- 당장 기록 조회 API 구현은 기존 exercise_sessions + Profile 기준으로 먼저 진행
- 장기적으로는 auth.users + profiles + user_settings 쪽으로 통합

즉:
- 지금 당장 큰 마이그레이션 하지 말고
- 기록 조회용 API는 현재 쓰는 user_id / UUID 체계에 맞춰 먼저 구현


10. 서버가 받아야 하는 요청 정리

A. 월간 운동 기록 조회

endpoint
- GET /api/records?userId={uuid}&year={yyyy}&month={mm}

예시
- GET /api/records?userId=f65f3f87-f292-43b0-92a5-3a3bc9820f12&year=2026&month=5

서버가 받아야 하는 값
- userId: uuid, 필수
- year: 숫자, 필수
- month: 1~12 숫자, 필수

서버 내부 처리
- month 시작일 계산
- 다음 month 시작일 계산
- exercise_sessions 에서
  - user_id = userId
  - started_at >= monthStart
  - started_at < nextMonthStart
  조건으로 조회
- 필요하면 Dance_class 조인해서 title 가져오기


B. 기간 운동 기록 조회 확장형

endpoint
- GET /api/records?userId={uuid}&startDate=YYYY-MM-DD&endDate=YYYY-MM-DD

서버가 받아야 하는 값
- userId
- startDate
- endDate

용도
- 나중에 주간 조회, 커스텀 조회에도 재사용 가능


C. 체중 추이 조회

endpoint
- GET /api/weight-history?userId={uuid}&months=6

서버가 받아야 하는 값
- userId
- months: 기본 6

서버 내부 처리
- weight_history 에서 user_id 기준 최근 N개월 조회
- 없으면 Profile 또는 profiles 의 현재 체중만 fallback 으로 내려줄지 정책 결정

12. 서버 저장 시 받아야 하는 값도 다시 정리

라이브 세션 종료 시 서버가 저장해야 하는 최소값:
- session_id
- user_id
- class_id
- started_at
- ended_at
- duration_seconds
- burned_kcal
- genre

추가 권장:
- movement_score
- total_frames

- user_weight_kg


13. SQL 관점에서 바로 필요한 작업 우선순위

1순위
- exercise_sessions 에 movement_score, created_at 정도 추가 검토
- exercise_sessions(user_id, started_at desc) 인덱스 추가
- /api/records 조회 API 구현

2순위
- weight_history 테이블 생성
- /api/weight-history 구현

3순위
- profiles / Profile 구조 정리
- class_id / Dance_class.videoId 명확화


14. 지금 상태에서 가장 현실적인 결론

바로 해야 할 최소 작업:
- exercise_sessions 를 기록 조회 원본으로 사용
- /api/records 를 userId + year + month 기준으로 구현
- weight_history 테이블을 새로 만들고 /api/weight-history 구현

즉 records 전용 테이블을 새로 만드는 것보다,
일단 existing exercise_sessions 를 잘 조회하는 방향이 더 빠르고 안전함


15. 서버 구현용 한 줄 정리

- 운동 기록 조회 원본: exercise_sessions
- 체중 추이 원본: 신규 weight_history
- 프로필 현재값: Profile 또는 profiles
- 기록 조회 API: /api/records
- 체중 추이 API: /api/weight-history
