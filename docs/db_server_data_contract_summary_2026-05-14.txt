DB/서버 연동 정리
작성일: 2026-05-14

목적
- 다크모드 같은 로컬 UI 설정은 앱 캐시로 처리한다.
- 그 외 사용자 데이터, 식단 기록, 운동 기록, 프로필, 클래스/영상 메타데이터는 DB + 서버 API 기준으로 관리한다.
- 이 문서는 "무엇을 서버로 보내야 하는지", "무엇을 서버에서 받아와야 하는지", "현재 구현돼 있는 것과 아직 비어 있는 것"을 정리한 문서다.

==================================================
1. 로컬 캐시로 두는 것
==================================================

앱 캐시/AsyncStorage/기기 로컬 상태로 충분한 항목
- 다크모드 on/off
- 푸시/운동 알림 on/off
- 배경음악 자동재생 on/off
- 임시 UI 상태
  - 현재 열어둔 모달
  - 현재 선택한 필터/정렬
  - 기록 탭의 현재 선택 월
  - 임시 입력값
- 서버 장애 시 임시로 들고 있을 화면 표시용 fallback 상태

원칙
- "기기 바뀌어도 유지돼야 하는 값"은 DB로 보낸다.
- "화면 편의용 상태"는 로컬 캐시에 둔다.

- foods[]

  - calories
  - confidence
- total_calories
- image_filename
- storage file path
- analyzed_at
- source
- note

D. 운동 세션 기록
- uuid
- session_id
- content_id
- dance_type
- started_at
- ended_at
- elapsed_seconds
- total_frames
- total_calories
- movement_score
- calories_burned(last frame 또는 frame 단위)
- user_weight

E. 클래스/영상 메타데이터
- content_id
- title
- genre
- subtitle/description
- level
- instructor
- duration
- kcal 예상치
- thumbnail/image URL
- guide video URL 또는 파일 경로
- tags[]
- goals[]
- steps[]
- 공개 여부
- 정렬용 값
  - 추천 점수
  - 인기 수강 수

중요
- 클래스 안에 들어갈 "가이드 영상"은 앱 번들 고정보다 서버/스토리지 URL 관리가 더 적합하다.
- 이유: 영상 교체, 썸네일 교체, 신규 클래스 추가, 비활성화가 서버에서 가능해야 하기 때문이다.

==================================================
3. 화면별로 서버에 보내야 하는 값 / 받아와야 하는 값
==================================================

3-1. 회원가입 / 로그인

회원가입 요청
- endpoint: POST /api/signup
- request body
  - name
  - email
  - password
  - age
  - created_at

회원가입 응답
- userId 또는 uuid

로그인 요청
- endpoint: POST /api/user/login
- query
  - Email
  - password

로그인 응답
- success
- userId 또는 uuid

비고
- 앱 코드 기준 파일
  - services/general-server-auth.ts

3-2. 프로필 화면

프로필 조회 요청
- endpoint: GET /api/profile/{uuid}

프로필 조회 응답
- uuid
- name
- email
- age
- password
- created_at
- height
- weight
- target_weight
- target_day
- target_kcal
- today_target_kcal
- bucket_profile_photo
- filepath
- profile_image_url
- current_streak

프로필 수정 요청
- endpoint: PUT /api/Profile/{uuid}
- request body(UserProfileUpdate)
  - name
  - email
  - password
  - age
  - created_at
  - weight
  - height
  - target_weight
  - target_day
  - today_target_kcal
  - current_streak
  - bucket_profile_photo
  - filepath
- multipart file
  - image

프로필 화면에서 DB로 유지해야 하는 값
- heightCm -> height
- weightKg -> weight
- targetWeightKg -> target_weight
- targetDurationWeeks는 현재 서버 필드가 직접 없으므로
  - 권장안 1: 앱에서 target_day 계산 후 target_day로 저장
  - 권장안 2: DB에 target_duration_weeks 컬럼 추가

비고
- 현재 profile.tsx는 화면 상태 위주이고 실제 fetch 연동은 제한적이다.
- 목표 기간은 현재 일반 서버 스키마에 직접 필드가 없다.

3-3. 홈 화면

홈 조회 요청
- endpoint: GET /api/home/{uuid}

홈 응답
- uuid
- day
- daily_target_burn_kcal
- today_target_kcal
- target_kcal
- daily_intake_kcal
- today_intake_kcal
- intake_kcal
- current_streak

설명
- 홈은 "프로필 + 오늘 식단 합계 + 목표 칼로리"를 조합해서 내려주는 요약 API로 쓰는 게 좋다.

3-4. 식단 화면

식단 분석 요청
- endpoint: POST /api/food/intake
- multipart form data
  - uuid
  - day
  - image

식단 분석 응답
- foods[]
  - label
  - calories
  - confidence
- total_calories
- image_filename
- source
- analyzed_at
- note

추가 조회 요청(일별 식단 기록)
- endpoint: GET /api/daily_food_intake/{uuid}/?year=YYYY&month=MM&day=DD

일별 식단 기록 응답
- UUID
- Day
- Foods[]
  - FoodName
  - Calories
  - Bucket_Name
  - File_Path
  - image_url
- TotalCalories
- RecordCount

설명
- 앱 food.tsx 기준으로는 분석 직후 응답만 받아서 화면에 보여준다.
- 기록 화면이나 홈 요약에 재사용하려면 "일별 조회" API를 같이 써야 한다.

3-5. 클래스 목록 화면

클래스 목록 조회 요청
- endpoint: GET /api/classes?genre={genre}&search={search}

이상적인 응답
- classes[]
  - content_id
  - title
  - genre
  - subtitle
  - instructor
  - level
  - duration
  - kcal
  - students 또는 popularity
  - rating
  - icon
  - color
  - tags[]
  - goals[]
  - steps[]
  - guide_video_url
  - thumbnail_url
- featured_ids[]

현재 상태
- 일반 서버 build_classes_payload()는 아직 True만 반환한다.
- 즉 클래스 데이터는 아직 실제 API가 아니라 앱 내부 정적 데이터에 의존 중이다.

권장
- 클래스 영상/메타데이터는 DB 또는 CMS/스토리지 기반으로 서버가 내려줘야 한다.
- 앱은 content_id만 신뢰하고, 상세 메타데이터와 guide_video_url은 서버 응답으로 받는 구조가 좋다.

3-6. 라이브 연습 세션

세션 시작 요청
- endpoint: POST /api/live/session/start
- request body
  - uuid
  - dance_type
  - content_id

세션 시작 응답
- session_id
- uuid
- status
- started_at
- transport
- stream_mode
- dance_type
- content_id
- ws_url

WebSocket 프레임 메타데이터(앱 -> 일반 서버)
- type: frame_binary
- UUID
- session_id
- frame_index
- total_frame
- image(bytes)
- user_weight

AI/일반 서버 분석 결과(일반 서버 -> 앱)
- type: frame_result
- session_id
- frame_index
- total_frames
- elapsed_seconds
- accepted
- calories_burned
- total_calories
- movement_score
- processed_at
- message

세션 종료 요청
- endpoint: POST /api/live/session/end
- request body
  - session_id

세션 종료 응답
- session_id
- status
- ended_at
- total_frames
- elapsed_seconds
- total_calories
- message

설명
- 기록 탭 원본 데이터는 사실상 이 세션 응답에서 만들어진다.
- 최소한 session end 시점에 records 테이블로 저장돼야 한다.

3-7. 기록 화면

권장 기록 조회 요청
- endpoint 예시 1
  - GET /api/records?userId={uuid}&year={yyyy}&month={mm}
- endpoint 예시 2
  - GET /api/records?userId={uuid}&startDate=YYYY-MM-DD&endDate=YYYY-MM-DD

기록 응답에 필요한 구조
- summary
  - totalKcal
  - totalMinutes
  - activeDays
  - sessionCount
  - avgKcalPerSession
  - peakWeek
- calendar[]
  - dateKey
  - day
  - kcal
  - minutes
  - count
- sessions[]
  - sessionId 또는 recordId
  - dateKey
  - performedAt 또는 startedAt
  - danceName
  - danceType
  - contentId
  - kcal
  - durationMinutes 또는 elapsedSeconds
  - movementScore

추가 체중 추이 조회 권장
- endpoint 예시
  - GET /api/weight-history?userId={uuid}&months=6

체중 추이 응답 권장
- currentWeightKg
- targetWeightKg
- history[]
  - dateKey 또는 monthKey
  - weightKg
  - note

현재 상태
- 일반 서버 build_records_payload()는 아직 True만 반환한다.
- app/(tabs)/record.tsx도 아직 더미 데이터 중심이다.

5. 지금 바로 서버/DB 연동 우선순위
==================================================

1순위
- 회원가입/로그인
- 프로필 조회/수정

- 기록 탭용 /api/records 실제 응답 구현

3순위
- /api/classes 실제 구현
- guide video URL, thumbnail URL, 추천/정렬 값 서버화

7. 최종 결론
==================================================

로컬 캐시로 둘 것
- 다크모드
- 알림 on/off
- 배경음악 on/off
- 임시 화면 상태

DB/서버로 관리할 것
- 계정
- 프로필/체형
- 프로필 이미지
- 식단 분석 결과와 일별 합계
- 운동 세션 기록
- 기록 탭 집계 데이터
- 클래스/영상 메타데이터
- 가이드 영상 URL

가장 중요한 서버 송수신 핵심값
- 프로필: uuid, height, weight, target_weight, target_day, today_target_kcal, current_streak, image
- 식단: uuid, day, image -> foods, total_calories, analyzed_at
- 운동 세션: uuid, dance_type, content_id -> session_id -> elapsed_seconds, total_calories, movement_score
- 기록 화면: summary + calendar + sessions
- 클래스: content_id 중심 메타데이터 + guide_video_url
